# 知识库辅助问题排查

专门结合 Obsidian 与 DBX MCP 排查问题。只在用户明确调用本 Skill 时使用，保留显式调用策略。知识库提供线索，当前证据决定结论。按以下六步执行，排查授权不等于修改代码或写入知识库的授权。

## 1. 检查 MCP 可用性

先发现当前会话实际提供的 Obsidian 与 DBX 工具，核对真实参数。结合项目、用户指定环境和已有上下文选择知识库与数据库连接，不固定工具前缀或连接名。存在多个知识库时明确目标库；无法判断且影响正确性时再询问。

通过最小只读请求验证目标 Obsidian 库的搜索、读取能力，以及 DBX 的连接发现和目标连接访问能力。仅看到工具名称或连接列表不代表目标服务可用；连接、环境或 schema 不明确时先确认，不得猜测或试探无关连接。此时只检查访问能力，业务数据查询留到第 3 步。

Obsidian 或 DBX 任一所需能力缺失、未能验证，或发生认证、授权、网络、TLS、进程及服务端故障时，说明失败环节、脱敏后的错误和未验证范围，主动询问是否需要协助配置，暂停本 Skill 后续排查。用户拒绝或尚未回复时，不得绕过 MCP 改用纯代码、文件直读或其他通道继续本 Skill。用户另行要求普通排查时，应明确已退出本 Skill。

协助配置须有用户明确授权，只处理其批准的服务和范围；不得索取或输出明文凭据，不擅自改连接、权限、安全校验或其他 MCP 配置。配置完成后重新验证，验证通过才进入第 2 步。后续步骤出现 MCP 故障时也返回本步骤。

不要将 SQL 语法错误、对象不存在、空结果或某个业务对象权限不足直接判为整个 MCP 不可用；区分访问能力故障与查询本身的问题。目标必需对象无法访问时，说明证据缺口，不尝试绕过权限。

## 2. 查询文档并报告命中依据

结合已有信息识别期望与实际结果、环境、时间、业务标识、异常、链路标识及影响范围。能从上下文或只读检查确定的内容自行确认，不一次性索要所有信息。

使用症状、业务术语、模块、异常码、接口、表或过程名检索目标库。优先阅读最相关的文章及章节，核对版本、适用条件、原因与处理步骤；必要时换同义词或缩小范围。连续检索无新增有效线索时结束检索，进入当前证据核验，避免无限扩展或遍读所有命中。

检索后明确报告：

- **命中知识库**：注明库名、实际采用的文章完整库内路径、章节，以及支持关联判断的具体内容或简短摘录；说明哪些症状和条件一致、哪些尚未核实。仅关键词相同不算有效命中。
- **未命中知识库**：完成检索仍无适用文章时，原样写出此句，并简述检索范围和主要关键词。未命中不阻止第 3 步。
- **未完成知识库检索**：检索未执行或中断时，原样写出此句并解释原因，不得冒充未命中；MCP 故障按第 1 步暂停。

## 3. 结合文档核验代码与数据库

读取工作区 `AGENTS.md` 等约束和相关实现，沿真实入口、调用链、配置、状态流转及外部交互定位问题。命中文章也必须用当前代码与运行证据核对，不能以文章解释得通代替核验；未命中时从现象建立候选原因。

围绕“现象 → 候选原因 → 能区分原因的检查 → 支持或排除 → 更新判断”逐步收敛。优先选择低成本、只读且能排除候选原因的检查；证据矛盾时先查明环境、时间、版本或业务粒度差异，不强行确认根因。可用日志应给出完整路径、相关时间和链路标识；没有日志不能证明某段逻辑未执行。

按问题选择代码、日志和数据的检查顺序。涉及单据状态、明细覆盖、回执、金额或数据一致性时，可尽早查库，不必等代码与日志穷尽。数据库查询必须有明确证据目标；无关时说明无需业务查询，不为满足流程查无关数据。

DBX 仅用于查询和查看定义。先确认目标连接、环境、schema，查看陌生对象的真实结构和关系，再执行有业务标识、时间或行数边界的最小范围查询，避免全表扫描和无关敏感数据输出。不得执行数据、结构、权限或事务变更，不调用业务存储过程、函数、包或作业；可使用经确认无副作用的内置查询函数。

需要数据库或存储过程修复时，只提供人工审阅方案，说明影响、前置条件、备份或校验、回滚与验证查询；无法回滚时说明原因和风险。本 Skill 不直接执行数据库修复。

## 4. 综合回答并区分事实与猜想

先给出当前结论，再给出能支撑结论的最小充分证据。清楚区分：

- **事实**：当前可核验的观察，标明出处及其证明范围。
- **推断或猜想**：说明依据、未证实的前提，以及需要什么检查才能确认或排除。
- **待确认事项**：缺失或矛盾的证据、对结论的影响，以及下一步最小检查。

关键结论引用知识库库名、文章路径与章节，代码文件路径、符号和必要行号，日志完整路径、时间与链路标识，或数据库连接环境、查询对象、查询条件和结果摘要。保留必要业务粒度和时间范围，对凭据、个人信息和无关生产标识脱敏。

静态代码只能说明逻辑或可能路径，不能单独证明某次生产请求实际走过该路径。区分代码原因、数据原因、外部系统原因和未决原因；证据不足时明确“尚不能确认根因”，不要将猜想写成事实。仅对影响业务、数据、范围、兼容性或验收的问题集中询问，给出选项、影响与建议。

## 5. 经用户明确同意后修改代码

提供具体修复方案、涉及范围、风险与验证方式，得到用户针对该修改的明确同意后才能编辑代码或项目配置。调用本 Skill、要求排查、认可根因或同意整理文档，均不等于授权修复；已明确授权同一修复范围时不重复索要同意。尚无证据支持的根因不得按猜想直接实施修复。

修改前重新检查相关调用链、现有实现及工作区状态，保留用户未提交的改动。只实施授权范围内的最小修复，不顺手重构；新发现的问题若改变业务、数据或兼容性范围，应先说明并确认。授权代码修复不解除数据库只读限制。

执行适合变更的编译、测试或静态检查，关注调用参数、返回值、边界和事务风险。分别报告已执行的本地验证、未执行项与原因，以及仍需 Oracle、HTTP、工作流或其他外部系统验证的内容，不把本地通过当作生产验证通过。

## 6. 总结、复盘与可选入库

排查或修复结束后，简要汇总现象与影响、文档命中情况、事实证据、根因或未决事项、排除的关键假设、已完成的修复及验证、剩余风险和下一步。未修复或未确认根因时如实说明，不伪装为已解决。

主动询问用户是否需要整理为 Markdown 复盘。只有用户明确同意后才起草；准备起草时阅读 [Obsidian 复盘入库规则](references/obsidian-writing.md)。整理 Markdown 的授权不等于写入知识库。

先展示完整待入库内容、目标库、目标路径及创建或更新范围，待用户审阅并明确同意该版本入库后才写入 Obsidian。已有完整草稿且用户已审阅并明确批准同一版本和范围时，不重复确认。内容或写入范围发生实质变化时重新提交审阅。
