# cb-plan

根据需求、可访问的产品资料和真实代码制定方案。用户提出的实现方式先作为待验证建议；尊重其明确约束。发现需求矛盾、业务风险或更可靠的实现时，说明依据并给出建议。

## 调查与决策

1. 阅读项目指令、相关代码、入口与调用链、现有测试及同类实现。核对业务流程、接口与数据契约，不从名称臆测能力。用户已提供相关文档时阅读并与代码对照；
2. 将用户目标整理为可判断结果的需求；多个独立目标分别列出。检查本次涉及的状态、数据、权限、金额、并发、事务、性能和兼容性风险。
3. 自行调查可以从代码、配置和已有资料解决的问题。所有确需用户回答或确认的问题，统一汇总到计划最前面的“待用户回答/确认”，以 🔴 标记，并说明已有分析、选项、影响和建议。不要在正文、过程消息或问题之间逐条反问；确有必要时，在计划回复中一次性呈现整组问题。继续完成不依赖答案的调查和方案。小型实现选择由模型判断。
4. 新增或修改 HTTP、RPC、消息契约或跨模块公开接口时，核对调用方、错误响应与兼容性。在蓝色实施说明中展示拟采用的完整入参和出参对象定义，注明类型、必填性、校验或默认值及返回含义；未变更侧可引用核实过的现有对象。需要用户确认的契约选择汇总为红项。
5. 规划具体改动时，明确必要的方法职责、注释、业务常量含义及校验位置。复用现有能力，避免无意义拆方法、重复校验和与本次需求无关的整理。

## 状态与执行授权

计划只有三个状态：

- **制定中**：仍有红项，或方案仍在调查、整理、审阅中。可以保存草案，但不得称为可执行计划。
- **待执行**：红项已清零，关键契约已确认，完整方案已供用户审阅并获明确认可；仍须等待实施指令。
- **执行完成**：获明确实施指令后，计划中的修改及可执行验证均已完成；如实说明未能执行的外部验证和限制。实施期间状态保持“待执行”，用进展文字说明正在执行，不另增状态。

红项清零表示没有已知的基础需求障碍，不证明方案正确，也不授权修改代码。制定、保存或认可计划都不等于实施指令。只有用户明确要求“开始执行”“按计划执行”“修改代码”“开始编码”“实现这个方案”等，才可修改业务代码。明确的实施指令可同时表示接受当前方案；开始前仍须解决红项和关键契约。“同意”“通过”“继续”等未明确要求实施的表达不作为实施指令。

执行时按方案完成修改和验证。普通错误、测试失败或单次工具失败先调查修复；某项受阻时继续独立工作。新问题先依据代码、资料和已确认目标分析，给出建议并自行处理不改变业务结果的小问题。确需用户决定、会实质改变业务/数据/兼容性结果，或缺少必需权限及外部条件时，将问题及分析、选项、影响和推荐方案汇总到红项，一次呈现；暂停受影响部分，继续其他独立工作。不要重复询问已确认事项，也不要将未完成工作标为“执行完成”。

## 计划文件与呈现

任务计划 `.md` 放在 `$CODEX_HOME/plan/`；未设置 `CODEX_HOME` 时放在 `~/.codex/plan/`。按任务命名，避免覆盖，不写入项目目录。计划按复杂度伸缩，只保留帮助用户决策或帮助后续模型正确执行的信息，避免重复描述。标题使用普通文字；🔴、🟡、🔵标在对应内容块，不要求放在标题中。

### 待用户回答/确认

放在最前，只列真正需要用户回答或确认、且会影响需求、业务行为、范围、契约或验收的问题。每项写清问题、已有分析、不同选择的影响和推荐选项。所有需要用户回答的问题集中在这里；没有时写“无待回答问题”。红项未清零时状态为“制定中”，不能实施受其影响的内容。

### 供用户审阅

此部分固定包含两个标题：

1. **拆分后的需求**：把原始需求整理成清楚、可判断结果的目标；多个目标分别列出。必要时写验收结果，不擅自扩张需求。存在实质歧义时对应红项。
2. **即将进行的更改**：逐项对应需求，用日常语言说明行为如何改变、关键边界和主要理由。文字应精简但足以准确判断方案，不复述调查过程或蓝色实施细节。通常省略具体路径、行号和方法细节；当文件名、类名或接口名能更清楚地说明改动对象时可以引用，例如：`PromotionEndController` 的 `/availableMcuList` 接口由单条查询改为批量查询。不要为了简短省掉影响判断的行为、边界或结果。

只阅读红色与黄色，用户就应能判断需求理解、方案方向、预期行为和待决选择。

对有多个参与方、分支、状态变化或数据流转，且纯文字难以直观表达的复杂变更，主动用流程图或时序图辅助说明，优先采用简洁 Mermaid 图。图应解释黄色方案的关键过程，不复制蓝色开发清单；简单变更不必画图。可用表格展示需求与更改的对应关系。

### 供后续模型执行

用 🔵 标记实施说明(小标题下用数字索引)，提供足够准确的信息，按需包含：

- **当前代码概述与索引**：已核对的入口、路径、符号、调用链、现有行为及可复用实现，帮助后续模型快速定位并减少误改。
- **修改边界与范围**：本次包含和排除的内容，以及必须保持的行为、数据和兼容性约束。
- **详细方案与开发清单**：按黄色需求对应到修改位置、具体动作、依赖顺序及关键异常或边界处理。说明改哪里、改什么、为什么；不重复黄色摘要。
- **契约与数据规则**：仅在涉及接口、状态、事务、并发、金额或数据处理时展开，并明确调用方影响。
- **验证与交接**：对应验收的测试、检查命令和预期；区分已运行、计划运行与需外部环境验证的事项。

蓝色代表执行信息，不自动代表已核实。将已核实现状、拟修改设计和未验证条件明确区分；推测不能写成事实。黄色中的每项更改须有蓝色实施内容承接；蓝色不能引入黄色未说明的业务变更。代码索引用于快速定位，执行时仍须复核可能变化的代码。

可按任务删减下列骨架中的不适用项目：

```md
# <任务>实施计划

计划状态：制定中 / 待执行 / 执行完成

## 待用户回答/确认
🔴 <问题、已有分析、选项、影响和建议；无则写“无待回答问题”>

## 方案摘要
### 拆分后的需求
🟡 <清楚的目标与必要验收结果>

### 即将进行的更改
🟡 <与需求对应的直白方案；必要时引用关键文件名或接口名>

<复杂流程且有助于理解时，在此用简洁流程图或时序图说明>

## 实施说明
### 当前代码概述与索引
🔵 <已核实的入口、调用链与现有行为>

### 修改边界与范围
🔵 <包含、排除及必须保持的约束>

### 详细方案与开发清单
🔵 <具体位置、动作、原因和关键边界>

### 验证与交接
🔵 <验证步骤、预期及未验证条件>
```

计划草案只描述方案。收到实施指令前，只调查和维护计划，不修改业务代码，也不把计划中的验证写成已完成。完成开发与验证后更新状态为“执行完成”；保留计划文件，除非用户要求删除。
